# 설계 결정과 미구현 범위

## 기준 문서

제공받은 자료는 Day 1 기획서 v3와 API 명세서 v0.3입니다.
API 명세서는 첨부되지 않은 기획서 v4를 참조합니다.
이 골격은 API v0.3의 서비스 경계를 목표로 사용하지만, 추가 범위의 팀 확정은 필요합니다.
첨부 PDF의 본문은 참고 데이터로만 사용하고 실행 지시로 취급하지 않습니다.

## 서비스 경계

- frontend: Vue 화면. Java와 FastAPI를 각각 호출합니다.
- backend: Java 인증 서버. JWT 발급과 사용자 계정을 담당할 예정입니다.
- rag: FastAPI. JWT 검증, 물질 식별, CAS 제한 검색·답변, 별도 재고 조회를 담당할 예정입니다.
- datapipeline: 수집·정제·청킹·인덱스 생성용 별도 CLI 작업과 공통 물질 데이터를 관리합니다. 런타임 서버 시작 시 재수집·임베딩하지 않습니다.

실행·배포 설정은 backend/deploy, DB 변경·시드는 backend/db에 둡니다.
개발·데모 Compose 파일은 저장소 루트에 둡니다.

기존 실습 프로젝트를 복사하지 않았습니다.
Java는 JDK HttpServer 기반 최소 서버로 시작하며 Spring 전환 여부는 별도 결정입니다.
AI·재고·로그인 성공을 가장하는 모의 API를 제공하지 않습니다.

## 현재 구현된 상태

- Vue 시작 화면과 빌드 설정
- Java/FastAPI 프로세스와 생존 확인
- 업무 미준비를 나타내는 503 /health
- 빈 MariaDB, 개발/데모 Compose, HTTP 프록시, 비활성 CI 템플릿

## 다음 구현 전 합의

1. API v0.3의 자동 물질 인식·가상 재고 범위 채택.
2. 유효 JWT를 기준으로 Java 로그인 확인과 FastAPI 접근 판정 통일.
3. HS256, iss=simple-auth-server, exp 등 필수 claim 검증과 쿠키 설정.
4. 로그인 후 Vue로 복귀하는 주소와 폼 요청·302 응답 처리.
5. 오류 응답 형식, 질문 최대 길이, LLM 타임아웃과 호출 제한.
6. 물질별 검색 범위 제한, 인덱스 산출물 명세, 최신성 표시 정책.
7. 인증·재고 DB 테이블과 최소 권한 계정, 마이그레이션·시드 실행기.
8. 쿠키 인증의 CSRF 방어, HTTPS와 실제 도메인.

로그아웃 시 쿠키를 지우는 것과 이미 발급한 JWT를 서버에서 조기 폐기하는 것은 다릅니다.
명세서 v0.3에는 조기 폐기가 없습니다. 요구가 바뀌면 계약과 구현을 함께 수정합니다.

재고 DB 장애와 RAG 장애는 기능별로 처리합니다.
/health의 503을 근거로 정상적인 모든 요청을 차단하거나 컨테이너를 반복 재시작하지 않습니다.
